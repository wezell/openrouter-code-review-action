# Bake-off comparison reference set

> **Sub-AC 1.1.3 deliverable.** Organize the captured Codex baseline
> findings — and their OpenRouter counterparts — into a structured
> per-PR comparison reference set with normalized fields, ready for
> A/B labeling and parity scoring.

This directory holds one normalized JSON record per sample PR plus a
sample-level `_index.json` rollup. Together they are the **single
input** the downstream labeling (Sub-AC 1.4) and scoring (Sub-AC 1.5)
sub-ACs read; nothing else has to re-walk the raw run artifacts.

## Why a separate reference set?

The bake-off has two parallel runners writing to two different trees
with two different ID conventions:

| Runner | Output | ID convention |
|--------|--------|---------------|
| `eval/run_codex_baseline.py` | `eval/runs/<eval_id>/codex.json` | `dotcms-core-35567` |
| `evaluation/bakeoff/run_openrouter.py` | `evaluation/bakeoff/runs/<pr_id>/openrouter.json` | `pr-35567` |

The findings inside each artifact are also **raw model output**:
nested `code_location.line_range.{start,end}`, severity encoded as a
free-form `[P0]`-style title prefix, no cross-run match information.

The labeling pass (methodology §2) and the parity scoring (§4)
expect a *normalized* per-PR record where:

* Every finding carries flat `path` / `line_start` / `line_end` /
  `severity` / `priority` / `confidence_score` / `title` / `message`
  fields — no nested code-location walks.
* Codex and OpenRouter findings are interleaved in a single
  `findings[]` array and tagged with `run` so a labeler reads them
  together (per methodology §2.4).
* Cross-run **match candidates** (same path + line proximity within
  `LINE_PROXIMITY_TOLERANCE` lines) are pre-computed so a human
  doesn't have to re-derive proximity for each finding.
* The capture state of each side is exposed as a single
  `labeling.status` rollup — `pending`, `awaiting_openrouter`,
  `awaiting_codex`, `ready_for_labeling`, or `ready_for_scoring`.

This is the comparison reference set: a *function* of the captured
artifacts, regenerated by `build_comparison_set.py` whenever those
artifacts change.

## Generating / refreshing

```bash
# Regenerate every comparison record from the current run artifacts.
.venv/bin/python -m evaluation.bakeoff.build_comparison_set

# Restrict to a single PR (e.g. after a re-capture).
.venv/bin/python -m evaluation.bakeoff.build_comparison_set --only pr-35567

# CI-friendly drift check: rebuild in memory, fail non-zero if the
# on-disk reference set differs from the rebuild. Use after every
# capture run to keep the reference set honest.
.venv/bin/python -m evaluation.bakeoff.build_comparison_set --check
```

The script is idempotent: re-running it overwrites every record. The
`generated_at` timestamp is excluded from `--check` comparisons so a
fresh-clone rebuild does not register as drift.

## Per-PR record schema

Each `pr-<n>.json` file conforms to:

```jsonc
{
  "schema_version": "1",
  "pr_id": "pr-35567",                 // matches evaluation/bakeoff/runs/<id>/
  "eval_id": "dotcms-core-35567",      // matches eval/runs/<id>/
  "repo": "dotCMS/core",
  "pr_number": 35567,
  "head_sha": "<merge-commit SHA — the exact diff reviewed>",
  "title": "<PR title>",
  "selection_rationale": "<why this PR is in the sample>",

  "diff_signal": {
    "additions": 0, "deletions": 3, "changed_files": 1, "loc_changed": 3,
    "surface": "backend",         // backend | frontend | infra | mixed
    "change_type": "bug_fix",     // bug_fix | feature | refactor | security | performance | infra
    "security_signal": false,
    "languages": ["java_or_kotlin"],
    "slots": ["real_bug_present", "multiline_suggestion"],
    "base_ref": "main",
    "head_ref": "fix/unique-fields-atomic-with-contentlet-save"
  },

  "runs": {
    "codex": {
      "artifact_path": "eval/runs/dotcms-core-35567/codex.json",
      "present": true,
      "capture_status": "pending",          // pending | captured | failed | missing
      "captured_at": null,
      "model": "gpt-5.4",
      "reasoning_effort": "medium",
      "web_search_mode": "disabled",
      "head_sha_at_capture": "<sha>",
      "head_sha_matches": true,             // matches PR head_sha at capture time
      "summary": {
        "overall_correctness": null,        // "patch is correct" | "patch is incorrect"
        "overall_explanation": null,
        "overall_confidence_score": null,
        "findings_count": 0,
        "carried_forward_count": 0,
        "by_severity": {"P0": 0, "P1": 0, "P2": 0, "P3": 0, "unknown": 0}
      },
      "carried_forward_count": 0,
      "notes": "<runner-supplied free-form note>"
    },
    "openrouter": {
      "artifact_path": "evaluation/bakeoff/runs/pr-35567/openrouter.json",
      "present": true,
      "capture_status": "unfilled",         // unfilled | skipped_dry_run | completed | error | missing
      ...
    }
  },

  "findings": [
    {
      "finding_id": "codex.f0001",          // stable per-run id
      "run": "codex",                       // codex | openrouter
      "raw_index": 0,                       // position in source array
      "path": "core-web/.../UniqueFieldsValidator.java",
      "line_start": 42,
      "line_end": 44,
      "severity": "P1",                     // P0 | P1 | P2 | P3 | null
      "priority": 1,                        // 0..3 | null (raw model value)
      "title": "🔴 [P1] ...",
      "message": "<finding body>",
      "confidence_score": 0.85,
      // labeling fields — populated by the human pass per methodology §2:
      "label": null,                        // TP | FP | DUP | CARRY | null
      "rationale": null,
      "matched_finding_id": null,           // for DUP, the id this duplicates
      "match_to_other_run": null            // id of the matching cross-run finding, if any
    }
    // ...openrouter findings are appended after all codex findings...
  ],

  "match_candidates": [
    {
      "codex_finding_id": "codex.f0001",
      "openrouter_finding_id": "openrouter.f0002",
      "path": "core-web/.../UniqueFieldsValidator.java",
      "line_distance": 0,                   // 0 = ranges overlap; 1..tolerance = adjacent
      "codex_line_range": [42, 44],
      "openrouter_line_range": [43, 45],
      "severity_match": true                // both findings carry the same severity tag
    }
  ],

  "labeling": {
    "status": "ready_for_labeling",         // pending | awaiting_openrouter | awaiting_codex
                                            //   | ready_for_labeling | ready_for_scoring
    "solo_labeled": null,                   // bool, set by the labeling pass
    "tolerance_lines": 3                    // ± lines used for match_candidates
  },

  "generated_at": "2026-05-07T02:06:46Z",
  "generator": "evaluation/bakeoff/build_comparison_set.py",
  "schema_doc": "evaluation/bakeoff/comparison/README.md"
}
```

The rules behind this shape:

* **Flat finding fields.** Methodology §2.2 lists the per-finding
  labeling fields (`path`, `line_start`, `line_end`, `severity`,
  `label`, `rationale`, ...). They map 1:1 onto this schema so the
  labeling pass can read each finding without a separate normalization
  step.
* **Both IDs preserved.** `pr_id` and `eval_id` both appear so any
  downstream tool that references either runner's tree can resolve.
* **`labeling.label` pre-allocated as `null`.** Reserving the field
  in the schema lets the labeling pass overwrite it in place. A tool
  that reads `findings[i].label` never has to branch on missing-vs-
  null.
* **Match candidates, not matches.** The script computes *candidates*
  (same path, line distance ≤ tolerance). Confirmed matches require a
  human (methodology §4.5) and are recorded by writing the partner's
  `finding_id` into `match_to_other_run` during labeling.

## Sample-level rollup (`_index.json`)

```jsonc
{
  "schema_version": "1",
  "generated_at": "2026-05-07T02:06:46Z",
  "generator": "evaluation/bakeoff/build_comparison_set.py",
  "sample_size": 10,
  "status_counts": {
    "pending": 10                            // status -> count across the sample
  },
  "prs": [
    {
      "pr_id": "pr-35567",
      "eval_id": "dotcms-core-35567",
      "head_sha": "<sha>",
      "labeling_status": "pending",
      "codex_status": "pending",
      "openrouter_status": "unfilled",
      "codex_findings_count": 0,
      "openrouter_findings_count": 0,
      "match_candidate_count": 0
    }
    // ... one row per sample PR ...
  ]
}
```

The index is the **operator dashboard**: a single read tells you
which sample slots are ready to be labeled and which are still
waiting on captures. The labeling pass picks PRs whose
`labeling_status` is `ready_for_labeling`; the scoring pass picks
those whose status is `ready_for_scoring`.

## Status semantics

```
                  codex.capture_status
                  ┌─────────┬──────────┐
                  │ ≠ captured │ captured │
                  ├─────────┼──────────┤
or.capture        ≠ completed │ pending │ awaiting_openrouter │
        _status   completed  │ awaiting_codex │ ready_for_labeling │
                  └─────────┴──────────┘
```

`ready_for_labeling` flips to `ready_for_scoring` once every finding
in the record carries a non-null `label`.

## How downstream Sub-ACs consume this

* **Sub-AC 1.4 (labeling)** reads each `pr-<n>.json` whose
  `labeling.status` is `ready_for_labeling`, walks `findings[]`,
  fills in `label` / `rationale` / `matched_finding_id` /
  `match_to_other_run`, and re-writes the file. Inter-rater
  agreement and `solo_labeled` are recorded on the `labeling` block.
* **Sub-AC 1.5 (overlap + FP-rate scoring)** reads each record whose
  `labeling.status` is `ready_for_scoring`, iterates `findings[]`
  with their final labels, applies the §4.3 / §4.4 metrics, and
  emits the bake-off report. P3 findings are excluded from the
  denominator per §4.4 — the `severity` field on every finding
  makes that filter a one-liner.

## Why the reference set is checked into git

* **Discoverable slots.** Each `pr-<n>.json` is a placeholder until
  the live captures arrive; committing them surfaces every sample
  slot rather than leaving labelers to discover gaps PR-by-PR.
* **Diff-able state changes.** A capture lands → `_index.json`'s
  `status_counts` shifts in a code-review-able diff. Silent regression
  (e.g. a re-capture that drops findings) shows up as a code-review
  red flag instead of a number on a dashboard.
* **Reproducible scoring.** Future model swaps re-run the same
  sample and rebuild the same comparison shape; historical records
  stay in-repo so trend tracking is a `git log` away.
